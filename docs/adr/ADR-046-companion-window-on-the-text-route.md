# ADR-046: One companion window per session on the text route

- Status: Accepted; builds on [ADR-023](ADR-023-open-in-a-window.md)'s window and adds the companion window [ADR-004](ADR-004-surfaces.md) planned and [ADR-011](ADR-011-surfaces-v0-1.md) left out of v0.1
- Date: 2026-10-21

## Context

In the v0.1.9 laptop test, Claude Code, Pi and OpenCode drew no card in plain macOS Terminal. Terminal.app has no inline image protocol, so Tiles picks the text route there by design: each reply gave the PNG path and `tiles open <id>`, and nothing else showed. `tiles setup` never said cards would not draw in that terminal. The product direction of 2026-10-17 said yes to a companion window beside the terminal, and ADR-004 names it as the fallback for terminals without pictures.

A window per card, as `tiles open` makes, would come to the front and take focus once per card, in the middle of the user's typing. ADR-023's window activates itself on purpose, since the user just asked for it.

## Decision

- **On the text route on macOS, `tiles run <harness>` keeps one companion window for the session.** It opens when the session's first card lands in the card cache and shows each later card of the session in the same window, in the order their geometry was written. Two cards that land between two looks at the cache (250 ms apart) show the later one.
- **It never takes focus.** `window.js` runs it as an accessory app (no Dock icon, no menu bar) in a non-activating `NSPanel` that is ordered front with `orderFrontRegardless`, never `activateIgnoringOtherApps` or `makeKeyAndOrderFront`. The terminal stays the frontmost app and keeps every keystroke. A non-activating panel leaves its app inactive when clicked, so clicking the card does not move focus either.
- **It sits beside the terminal.** On first opening it reads the bounds of the front on-screen window of the terminal's app from `CGWindowListCopyWindowInfo`, which needs no permission (window titles would need Screen Recording; bounds do not). The app is the one `__CFBundleIdentifier` names in `tiles run`'s environment, which macOS sets for a shell started from an app, else the frontmost app. It picks the screen holding the centre of the terminal's window first and sizes the card for that screen: the card's drawn size (its PNG's pixels over that screen's scale) within 90% of the screen. The window goes right of the terminal's window when that screen has room, else left of it, else at that screen's right edge, level with the terminal's top. With no terminal window found it takes the main screen's top right. It keeps the card's shape when resized, and each later card keeps its top-left corner while the new frame fits inside its screen's visible frame; otherwise the window shifts back inside, flush with the right or bottom edge, and never past the left or top edge. The window stays whole on one screen. Its light or dark appearance follows the theme in the card's geometry. Reading the terminal's position through Apple Events would raise an Automation prompt, so the window does not.
- **Its lifecycle follows the session.** Closing the window leaves the harness running; the next card of the session opens it again, placed afresh. It closes when `tiles run` exits: `tiles run` ends the `osascript` process and removes the file the window follows. The window also ends itself when that file goes or when its parent is gone (`getppid()` is 1), so a `tiles run` killed without cleaning up leaves no window behind. It runs in its own process group, so no signal the terminal sends the harness reaches it.
- **Only this session's cards show.** `tiles run` now passes `TILES_SESSION` on the text route too, and the window shows a card only when its geometry names that token, as the wrapper draws only such cards (ADR-024). Another `tiles run`'s cards and those `tiles open` draws in a plain shell never reach it.
- **It is ADR-023's window, extended.** `window.js` takes a second form, `follow FILE BUNDLE` (a plain word: `osascript` reads a leading `--` as its own option), where FILE holds three lines, the PNG path, the title and `light` or `dark`. `tiles run` rewrites it whole (a file beside it, then a rename) for each card, and the script reads it every 250 ms and swaps the picture in place. No compiled helper is needed, because JavaScript for Automation reaches every AppKit call the window uses. The title passes the sanitizer, which also keeps it to one line.
- **`TILES_WINDOW=off` turns it off**, as it does `tiles open`'s window; so do `0`, `false` and `no`, in any case. The text route then gives the PNG path and `tiles open <id>` as before. `tiles open <id>` is unchanged, and inside `tiles run` still draws no window of its own.
- **Setup and doctor say so.** On a terminal whose route is text, `tiles setup` (when the environment names the terminal) and `tiles doctor` print one `pictures:` line: cards will not draw inline in this terminal, Warp, Ghostty, kitty, iTerm2 and WezTerm draw them inline, and how cards open here (the companion window, or with `TILES_WINDOW` off the PNG path and `tiles open`).
- With `TILES_TRACE` set, `tiles run` logs `window: opened with <id>`, `window: swapped in <id>`, `window: closed by the user` (logged when the next card reopens it) and `window: closed as tiles run ended`.

## Consequences

- Inline routes are unchanged: no wrapper runs on the text route, and no other route opens the window.
- The chart result on the text route first still asked the model to give the PNG path and named `tiles open <id>`. In a real `tiles run claude -p` session in Terminal.app on 2026-10-21 the reply said `tiles open <id>` would open the chart in its own window while the companion window already showed it. Since 2026-10-21 `tiles run` also passes `TILES_COMPANION=1` beside `TILES_SESSION` wherever it keeps the window, and the server's text-route result then says the user already sees the card in the Tiles window beside the terminal, asks the model to say so in one line without asking the user to open anything, gives the PNG path for reference and leaves out the `tiles open <id>` line. The session instruction says the same wherever it goes (Claude Code's `--append-system-prompt`, Codex's `developer_instructions`, the MCP `instructions`, and the Pi and OpenCode instruction files `tiles run` writes) in place of asking for the PNG path so the user can open it. The server learns of the window only from that variable, never from the terminal. With the window off, not under `tiles run`, or off macOS, the result is as before.
- The window shows the PNG at the terminal's pixel density, as ADR-023's does: no hover, no filters, no card history. Off macOS there is no window, and Linux terminals keep the text route as it was.
- Stage 4 can grow from this window: a card history to step back through, hover values read from the card's call, or a window that follows the terminal when it moves. Each would need the window to keep more than the newest card's file.
- The window's process shows as `osascript` in Activity Monitor; as an accessory app it is not in Cmd-Tab or the Dock.
