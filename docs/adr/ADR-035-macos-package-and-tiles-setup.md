# ADR-035: One macOS package installs a universal `tiles` and opens `tiles setup`, which sets Tiles up for every harness on `PATH` after one question; `install.sh` removes the quarantine flag and refuses a binary that does not run

- Status: Accepted; its rule that `tiles setup` never removes Claude Code's `tiles` server is superseded by [ADR-039](ADR-039-setup-replaces-a-stale-claude-code-server.md), which replaces a user-scope server for another `tiles` after the same question; adds the package to [ADR-022](ADR-022-sealed-assets-and-releases-only-channel.md)'s release files and its signing steps, and leaves an install the package made to the next package in [ADR-032](ADR-032-update-command-and-harness-versions.md)'s `tiles update`
- Date: 2026-10-20

## Context

The owner, on installing Tiles, 2026-10-18: "why can't i just download 1 file from github from [the releases page], double click it and it installs? and why do i have to run so many commands in terminal in step 2? also users shouldn't have to manually install tiles install claude, tiles install pi etc. they install it once in their macbook by some command in terminal like brew install tiles, and it auto installs for all AIs, harnesses, terminals, warehouses, semantic layers, Bi tools." And on the product generally: "We want speed, craft and a polished product and the best user experience."

A first install on a laptop (Apple Silicon, v0.1.0, the archive downloaded in Chrome) printed `installed <home>/.local/bin/tiles ()`, an empty version, and the binary was gone before the next command. The archive carried `com.apple.quarantine`, which `cp` and `tar` pass on to the files they write; most likely Gatekeeper stopped the unsigned, quarantined binary when `install.sh` ran its `--version`. `install.sh` printed `installed` regardless. `tiles update` already removed the flag ([ADR-032](ADR-032-update-command-and-harness-versions.md)); `install.sh` did not.

Installing then took a download, the `TILES_ARCHIVE` command, an `xattr` step, and one `tiles install <harness>` per harness. The open-core plan dropped the Homebrew tap, so one file from the release page and one setup command take its place. The data logins Tiles supports today are Omni ([omni.md](../omni.md)) and the BigQuery warehouse ([ADR-031](ADR-031-warehouse-sources.md), [ADR-033](ADR-033-warehouse-query-path.md), [ADR-034](ADR-034-warehouse-surface.md)). A terminal needs no setup: `tiles run` picks the route when it starts.

## Decision

### `install.sh` removes the flag and checks the binary runs

- It removes `com.apple.quarantine` from its own copy of the archive, the unpacked binary and the installed `tiles`, each with `xattr -s`, which acts on a symlink itself and never follows it, as `tiles update`'s `lremovexattr` does. The download in `~/Downloads` is left as it is. A flag it cannot remove stops the install.
- It calls the install done only when the installed `tiles --version` exits 0 and prints a version. Otherwise it prints that the binary did not run (or that it was removed as soon as it was written), names Gatekeeper and the laptop's endpoint security software, says to choose Open Anyway in System Settings > Privacy & Security or ask IT to allow `tiles`, and exits 1. It never prints `installed` for such a binary.
- With standard input and output both a terminal, it then runs the installed `tiles setup`, which asks once, no by default. Otherwise its last line names `tiles setup`.

`scripts/test_install.sh` covers a quarantined archive (the installed binary carries no flag, the download keeps its own), a binary that prints nothing, dies on a signal, or deletes itself, and both endings: under `script`'s pseudo-terminal it runs `tiles setup`, and with its output in a file it names it.

### `tiles setup [--yes] [--dry-run]`

- **It finds** each harness Tiles supports on `PATH` (Pi, OpenCode, Claude Code, Codex), the terminal by its environment, a `tiles` earlier on `PATH` than the one running, and what each data source can see without reading or copying a secret. Omni: `TILES_OMNI_URL`, whether `TILES_OMNI_API_KEY` is set (never its value), the Keychain's `tiles.omni/url` item, which holds no secret, and whether a `tiles.omni/api-key@<host>` item exists, found by a Keychain search that asks for no attributes and no data, so the key is never read. The same check decides whether the installs it plans treat Omni as configured, which `tiles install` decides by reading the key. A registered source reports through `Source::found` ([ADR-031](ADR-031-warehouse-sources.md)'s seam), so `tiles-cli` still names no warehouse. The warehouse: its settings when configured; else the Google credentials file `adc_path` names and its `type` alone (only that field is deserialized, and the bytes are overwritten), the dbt project `find_project` finds, and whether a `profiles.yml` is in `DBT_PROFILES_DIR`, the project or `~/.dbt`, never opened since it may hold credentials.
- **It plans** each harness with the steps `tiles install <harness>` would run ([surfaces.md](../surfaces.md)), and calls a harness set up when every step would change nothing: each file already holds the bytes the install writes, Codex's `[mcp_servers.tiles]` already runs this `tiles` with `mcp` and `TILES_DRAW=text` (and already asks, when a data source is configured), and Claude Code's own `claude mcp get tiles` prints a server whose `Command:` is this `tiles`, whose `Args:` are `mcp` and whose `Environment:` holds `TILES_DRAW=text`. An install for another `tiles` or an older add-on is planned again, except Claude Code's: a `tiles` server there that runs another command, or lacks `mcp` or the variable, reads `claude: <path>, set up with another tiles, <command>; run claude mcp remove tiles --scope user, then tiles setup` (or `set up with this tiles, but not with mcp and TILES_DRAW=text`), and setup changes nothing there, since `claude mcp add` refuses a name that exists and removing the user's registration is left to a later change. An install that would overwrite the user's own `OpenCode` `config.json` or Codex approval setting is reported with `tiles install`'s refusal and left alone.
- **It prints one list and asks once.** `Tiles found:` with one line per item, `Tiles will change:` with each step, then `Set up Tiles for Claude Code and Codex? [y/N]`. Only `y` or `yes`, in any case, goes ahead; no answer, an empty line, end of input or anything else changes nothing. `--yes`, the one spelling, answers for a script; `--dry-run` prints the list and changes nothing. With nothing to change it asks nothing; when a harness is left for the user, refused or set up with another `tiles`, it says `Nothing for Tiles to change; see the lines above.` in place of `Every harness on PATH that Tiles can set up already has it`. On yes it runs each harness's steps through the same `install::apply` as `tiles install`, reports each, carries on past a failure and exits 1 if any failed. Then it prints the commands that finish each data source it found but could not finish: `tiles omni set-key https://<host>`, `gcloud auth application-default login`, `tiles warehouse setup --billing-project <id> --project <id> [--dbt-project <dir>]`. It never runs them: each needs a key or a choice only the user has.
- **Running it again changes nothing**: every harness it set up reads `already set up`.
- **`tiles doctor`** runs the same plan, with the same Omni check, and prints `  setup: Tiles is not set up, or is out of date, for Pi and Codex; run tiles setup` after the harness rows when any harness on `PATH` would be set up. `claude mcp get` starts the `tiles` server to check it, so doctor never runs it: it reads Claude Code's user-scope registration from `~/.claude.json` (`mcpServers.tiles`, its `command`, `args` and `env`) and nothing else from that file. No entry puts Claude Code in that line; an entry for another `tiles`, or without `mcp` and `TILES_DRAW=text`, adds `  setup: Claude Code is set up with another tiles, <command>; run claude mcp remove tiles --scope user, then tiles setup`; a missing or unreadable file, or one of another shape, leaves Claude Code out of doctor's lines. That read is only a hint: `tiles setup` decides through `claude mcp get`, which also sees a server in another scope or config folder.

`crates/tiles-cli/src/setup/tests.rs` covers the plan, the Omni lines, the question and every answer; `crates/tiles-cli/tests/setup.rs` runs the binary in a temporary `HOME` with stub harnesses that log each call: no answer or `n` writes nothing and runs no `mcp add`, yes sets up all four, a second run finds all four set up, a Claude Code server for another `tiles` is named and neither removed nor added, and `tiles doctor` offers `tiles setup` until then; with no `~/.claude.json`, a file of another shape, no `tiles` entry, one for another `tiles` and one for this `tiles`, doctor's lines leave Claude Code out, offer it setup, name the other `tiles`, and say nothing, and the stub `claude` is never called.

### The package

- **One file per release**, `tiles-<tag>-macos.pkg`, built in the `sign` job by `scripts/package-macos.sh` after `scripts/sign-macos.sh`: Apple's tools only, no dependency code, so the job stays the one that may hold Apple secrets. It checks each tarball against its hash, joins the two binaries with `lipo` into one universal `tiles`, keeps a Developer ID signature `sign-macos.sh` made or else signs it ad hoc, checks `--version` prints the tag, and builds the package with `pkgbuild` and `productbuild` (identifier `io.github.tileshq.tiles`, both architectures, the startup disk only, no choices). The publish job checks the package's hash, adds it to `SHA256SUMS` and uploads it first; the release notes lead with it.
- **It installs** `/usr/local/bin/tiles`, which is on every Mac's default `PATH` through `/etc/paths`, and `/usr/local/share/tiles/` with `LICENSE` and `tiles-setup.command`.
- **Its postinstall opens `tiles setup` where the user sees it.** It runs as root, finds the person signed in at the screen with `stat -f %Su /dev/console`, and runs `launchctl asuser <uid> sudo -u <user> open -a Terminal /usr/local/share/tiles/tiles-setup.command`: a Terminal window running `tiles setup` as that person, which asks before changing anything. When no one is at the screen, the target is another volume, `installer` runs it from a shell (`COMMAND_LINE_INSTALL`), or Terminal does not open, it prints `open Terminal and run tiles setup` to the install log. It always exits 0, since `tiles` is installed either way. The installer's first page says Terminal will open and that nothing changes until the user answers `y`; its last page says to run `tiles setup` if no window opened.
- **`tiles update` leaves it to the next package.** Run from `/usr/local/bin/tiles` without `TILES_BIN_DIR`, `tiles update` would write a second copy to `~/.local/bin`, so it says to download `tiles-<tag>-macos.pkg` from the latest release and open it, and exits 1. `--check` and the daily notice name that package for a newer release, never `tiles update`.

`scripts/test_package.sh`, in the macOS `rust` job, builds a package from two stub binaries, expands it, and checks the universal ad-hoc-signed `tiles`, the setup command, the postinstall, both architectures and the last page; a tampered tarball and a tag that is not `vX.Y.Z` are refused; and the postinstall, with stub `stat`, `id` and `launchctl`, opens Terminal as the person at the screen and otherwise prints the next step and exits 0. No test installs the package: that needs an administrator and changes the machine.

### Signing the package later

`package-macos.sh` signs and notarises the package when `APPLE_INSTALLER_IDENTITY` is set, through its `sign_package` function. Until then the job warns that the package ships unsigned. With the Apple Developer account, these steps add it, beside [ADR-022](ADR-022-sealed-assets-and-releases-only-channel.md)'s six secrets:

1. Create a "Developer ID Installer" certificate (Xcode, Settings, Accounts, Manage Certificates, then +). It is a different certificate from the "Developer ID Application" one that signs the binary.
2. Export it with its private key from Keychain Access as a `.p12` with a password. `APPLE_INSTALLER_CERTIFICATE` is the file in base64; `APPLE_INSTALLER_CERTIFICATE_PASSWORD` is that password; `APPLE_INSTALLER_IDENTITY` is its name as `security find-identity -v` prints it, such as `Developer ID Installer: <name> (TEAMID1234)`. Add each with `gh secret set <NAME> --env release --repo tileshq/tiles`, then delete the `.p12`.
3. Pass the three, and ADR-022's `APPLE_ID`, `APPLE_TEAM_ID` and `APPLE_APP_PASSWORD`, to the "Build the installer package for every Mac" step's `env` in `.github/workflows/release.yml`. The script then imports the certificate into a keychain of its own, signs with `productsign`, notarises with `notarytool --wait`, staples the ticket, and deletes the keychain.

That path has not run yet: it waits for the account.

## Consequences

- **An unsigned package asks to be allowed once.** On macOS 15 and later, opening it shows that Apple could not check it for malicious software; choose Done, open System Settings > Privacy & Security, choose Open Anyway beside the package's name, then open it again and enter an administrator password. On macOS 14 and earlier, Control-click the package and choose Open. A signed and notarised package opens without either.
- **A managed laptop may block it.** Device management can refuse unsigned installers outright, and endpoint security software can delete an unsigned binary the moment it is written. Then the person asks IT to allow Tiles, or waits for the signed package.
- **The package needs an administrator**, since it writes `/usr/local/bin`. Without one, `install.sh` installs into `~/.local/bin` as before.
- **Two copies can coexist.** A package install beside an earlier `install.sh` one leaves `~/.local/bin/tiles`; the harnesses `tiles setup` sets up run the one running, and since 2026-10-21 setup offers to move a copy ahead of it on `PATH` aside (below).
- **Claude Code is set up once.** A `tiles` server that runs another `tiles` is named with the two commands that replace it, and the user runs them; `tiles setup` never removes it. `claude mcp get` starts the server to check it, so `tiles setup` waits up to 20 s for it; `tiles doctor` reads `~/.claude.json` instead, so a server Claude Code keeps elsewhere, as with `CLAUDE_CONFIG_DIR`, shows only in `tiles setup`.
- **Uninstalling** is `sudo rm /usr/local/bin/tiles && sudo rm -r /usr/local/share/tiles && sudo pkgutil --forget io.github.tileshq.tiles`, then each harness's own removal (`claude mcp remove tiles --scope user`, `codex mcp remove tiles`, and the files [surfaces.md](../surfaces.md) lists).
- The package has not yet been opened on a laptop; the first release that carries it is checked there before this record's limits are taken as measured.

## Changes since

- 2026-10-21, the other copies on `PATH`. On the v0.1.9 laptop check the package's `/usr/local/bin/tiles` set the harnesses up, but `~/.local/bin/tiles` 0.1.2 from an earlier `install.sh` came first on `PATH`, so in Warp `tiles --version` said 0.1.2 and `tiles setup` was an unknown command, and setup only said the harnesses would run the new one. Now `tiles setup` names every other `tiles` on `PATH`, ahead of or behind the one running, with the version its `--version` prints within 5 s (sanitized; `which printed no version` otherwise). A file reached through a symlink or hard link to the running one is not another copy, and a directory `PATH` names relatively is skipped. A copy ahead of the running one that is the same version or newer is named so (`is newer than this one (<this>, version <v>) and comes first on PATH, so a terminal runs it`) and never offered a move. One that is older, or whose version cannot be read as a release's `X.Y.Z` (a development build's 0.0.0 counts as unreadable), and that the user owns, is offered: with a terminal on standard input and output it is listed under `Tiles will change:` as `tiles: move <path> aside, to tiles-<version>-old beside it` (`tiles-unknown-old` for one with no version, `-2` to `-9` when the name is taken), and setup asks `Move <path> aside, to <new path>? [y/N]`, no by default, after the harness question. On `y` it renames the file, never deletes it, and says to open a new terminal tab or run `hash -r` (`rehash` in zsh). Without a terminal, with `--yes`, or with `--dry-run`, setup lists no move and prints `mv -n <path> <new path>` instead, as it does after `n`. A copy owned by another user is named with `sudo mv -n <path> <new path>` and never moved. When the running `tiles` is not on `PATH` at all, as for a development build, the copies are only named. `tiles doctor` prints one line per copy ahead of the running one, under its version line, an older one ending `move it aside: mv -n <path> <new path>`. `crates/tiles-cli/src/copies.rs` and `crates/tiles-cli/src/setup/tests.rs` cover an older copy ahead, a newer or same one ahead, a newer one behind, one owned by another user, one that prints nothing, one that never answers, and every answer to the question, with fake `PATH` directories.
