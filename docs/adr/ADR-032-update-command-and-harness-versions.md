# ADR-032: `tiles update` installs a checksum-verified release, a daily check names a newer one, and `tiles run` names a harness version Tiles was not proved on

- Status: Accepted; amends [ADR-001](ADR-001-product-scope.md)'s "update checks" non-goal and its one outbound connection, [ADR-005](ADR-005-privacy-and-secrecy.md)'s "no update checks", and [ADR-024](ADR-024-security-baseline-in-ci.md)'s "no update check", and adds `api.github.com` and `github.com` to ADR-024's documented hosts, named only by `crates/tiles-cli/src/update.rs`
- Date: 2026-10-19

## Context

The owner, 2026-10-19 13:30, asked whether Tiles should watch harness releases, keep itself current and give users an update command: "yes to all, ideally we have auto checks to check for updates across all harnesses. As soon as there is one, a worker updates the with the new build. users who use tiles simply get a command update tiles by typing tiles update like most things do like for pi updates it always says at launch update pi by typing pi update etc." Earlier that day he installed v0.1.1 on a laptop by hand. Gatekeeper deleted the quarantined binary, and the install left `~/.local/bin` off his `PATH`. Removing the `com.apple.quarantine` attribute from the archives before running the installer fixed it.

A maintainer already watches harness releases and re-proves Tiles on each new one. This record is the user-facing half. Before it, Tiles had no update path but `scripts/install.sh`, [ADR-024](ADR-024-security-baseline-in-ci.md) said Tiles sends no update check, and the only harness version Tiles compared was OpenCode's ([ADR-029](ADR-029-opencode-launcher-standalone.md)).

Releases live in a releases-only repository ([ADR-022](ADR-022-sealed-assets-and-releases-only-channel.md)), and `gh repo view --json visibility` printed `PRIVATE` for it on 2026-10-19. The releases move to a public repository at the open-core launch.

## Decision

### `tiles update [--check] [--allow-older] [vX.Y.Z]`

- **The releases location is one constant.** `RELEASES_REPO` in `crates/tiles-cli/src/update.rs` names that repository, and `TILES_RELEASES_REPO=<owner>/<repo>` overrides it for `tiles update`, the daily check and `scripts/install.sh`, which still reads its older `TILES_REPO` when `TILES_RELEASES_REPO` is unset. A value that is not `<owner>/<repo>` stops the daily check, and `tiles doctor`'s line names it. The public launch changes the constant and `the_releases_location_is_one_constant_with_an_override`.
- **The download goes through `gh` or a download by hand.** With `gh` on `PATH` and `gh auth status` succeeding, `tiles update` reads the latest tag with `gh release view --repo <repo> --json tagName --jq .tagName`, unless a tag is named, and runs `gh release download v<X.Y.Z> --repo <repo> --dir <dir> --pattern tiles-v<X.Y.Z>-<target>.tar.gz --pattern SHA256SUMS` into an owner-only directory of its own under the temporary directory. Without `gh` signed in, `TILES_ARCHIVE` and `TILES_SUMS` name an archive and `SHA256SUMS` downloaded by hand. With neither, it prints the steps and exits 1: open the release page in a browser signed in to GitHub, download the two files, and run `TILES_ARCHIVE=~/Downloads/<archive> TILES_SUMS=~/Downloads/SHA256SUMS tiles update`.
- **The archive is checked first.** Tiles reads the archive once, hashes those bytes with SHA-256 (`ring`, already linked through rustls), and compares the hash with the `SHA256SUMS` line that names the archive. A missing line, two lines with different sums, or a mismatch refuses the update, and nothing is replaced. Only the checked bytes are unpacked: `tar -xzf` extracts the one member `tiles-v<X.Y.Z>-<target>/tiles`, which must be a regular file.
- **The quarantine flag is removed.** On macOS, Tiles removes `com.apple.quarantine` from a by-hand archive and its `SHA256SUMS`, and from the unpacked binary, before it runs anything. Files fetched by `gh` carry no flag.
- **The replace is one rename.** The new binary is written beside the installed one in the same directory, as `.tiles.update.<pid>.<n>` (created new, mode 0755, synced), then its `--version` is run with ADR-029's reader: stdin closed, the answer in an unlinked file, at most 5 s. Unless it names the release's version, the file is removed and nothing is replaced. Otherwise it is renamed over `$TILES_BIN_DIR/tiles`, else `~/.local/bin/tiles`, which is where `install.sh` puts it. A process still running the old file keeps it until it exits.
- **One line reports it.** `updated tiles from 0.1.4 to 0.1.5 at <home>/.local/bin/tiles`. When that folder is not on `PATH`, a second line prints the `export PATH` line, as `install.sh` does. When the `tiles` that ran is another file, a line names it.
- **No downgrade by accident.** An older release is refused unless `--allow-older` is passed. The installed release prints `tiles 0.1.5 is already release v0.1.5; nothing to update`.
- **`--check` only reports.** It reads the latest release through `gh` when signed in, else through the anonymous `GET` below, and prints `Tiles vX.Y.Z is available; run tiles update`, or that this is the latest or newer. It takes no tag.
- Release builds exist for macOS only, so elsewhere `tiles update` refuses with `install.sh`'s message.

### A laptop without `gh`, until the launch

The repository was private at the time, so GitHub answered an anonymous request for its metadata with 404. On a laptop without `gh` signed in, `tiles update --check` says that and exits 1, and `tiles update` prints the by-hand steps. The browser session that downloads the two files must belong to an account the owner gave read access. `tiles update` then removes the quarantine flag the browser added, the step that failed on 2026-10-19. After the launch the same steps work without a sign-in. Tiles still does not download release assets itself: GitHub answers an asset's URL with a redirect to `release-assets.githubusercontent.com`, and `tiles-net` follows no redirects.

### The daily check and the launch notice

- **When.** `tiles run <harness>` (not `--dry-run`) and `tiles doctor` check at most once in 24 hours per user, and only in a release build: a 0.0.0 build never asks.
- **The gate.** The check's state is `update-check.json` in `$TILES_STATE_DIR`, else `$XDG_STATE_HOME/tiles/`, else `~/.local/state/tiles/`. The file is owner-only, written through a fresh file renamed over, and never in the card cache that `tiles cache clear` empties. It holds `checked`, the time of the last check in seconds since the epoch, and `latest`, the newest version seen. Tiles writes the timestamp before the request, so a check that fails or is killed still counts. A clock set back makes the check due. With no state directory there is no check.
- **What it sends.** One `GET https://api.github.com/repos/<owner>/<repo>/releases/latest` over `tiles_net::Client`: HTTPS with the system trust store, no redirects followed, the proxy from the environment, and a 2 s deadline. The request carries `Host: api.github.com`, `User-Agent: tiles/<version>` and `Accept: application/json`, and no other header: no cookie, token, `Authorization`, machine or user id, and nothing about the harness, the cards or their data. `a_get_sends_the_host_user_agent_and_accept_only` in `crates/tiles-net/src/lib.rs` holds the client to that header list. GitHub sees what any HTTPS request shows: the address it came from, the time and the Tiles version.
- **What it reads.** Only `tag_name`, accepted when it is `vX.Y.Z` in digits, from at most 1 MiB of response.
- **The notice.** When the newest release seen is newer than the running binary, `tiles run` prints `Tiles vX.Y.Z is available; run tiles update` on stderr before the harness starts and again after it exits, since a harness that clears the screen on start wipes the first, and `tiles doctor` prints it under its version line. Tiles keeps printing it until `tiles update` runs. The line never goes into a card, a tool result or the MCP server's output. A failure of any kind prints nothing.
- **How long `tiles run` waits.** The check runs in a thread while the terminal is asked and the engine loads. The notice is printed if the check finishes within 2.25 s of the start; a later answer is still written to the state file and shows at the next start.
- **The off switch.** `TILES_UPDATE_CHECK` set to `off`, `0`, `false` or `no`, in any case, sends nothing and writes nothing; any other value leaves the check on. `tiles doctor` prints an `update check:` line with the value it read, how long ago the last check ran (`40 min ago`, `3 h ago`, `2 d ago`) and the newest release seen.
- **The binary never updates itself.** Only `tiles update` replaces it, when the user runs the command.

### Harness versions

- **The table.** `PROVED` in `crates/tiles-cli/src/proved.rs` has one row per harness: Pi 1.0.0, 1.2.0, 1.3.0 and 1.4.0 and Claude Code 2.1.309 (this record, "Versions proved since"), Codex 0.163.0 ([ADR-011](ADR-011-surfaces-v0-1.md)) and 0.164.0 (this record), and OpenCode's two rows as ADR-029 names them, 1.19.3 for sst/opencode and 2.0.32 for the launcher (`PROVED_PUBLIC`, `PROVED_LAUNCHER`). A row can list several versions, oldest first. An installed version counts as proved when it matches any of them by the parts its harness compares, and every line below names the newest. A maintainer changes a row once Tiles is proved on the new release, adding the version when users stay on the older ones (Pi, 2026-10-21) and replacing it otherwise.
- **`tiles run`.** It reads `<harness> --version` in a thread with ADR-029's reader while the terminal is asked. For Pi, Claude Code and Codex, a major and minor version that matches none in the row prints one line on stderr before the harness starts and again after it exits, such as `Tiles was proved on Claude Code 2.1.309, and this is 2.2.0; if a card misdraws, run tiles check`. OpenCode keeps ADR-029's rule, the major version, against the row of the command line its `--help` names. A version that cannot be read prints nothing. A dry run prints the same line on stderr, and its stdout is unchanged.
- **`tiles check`.** A `<harness> version:` line follows each of Pi's, Claude Code's and Codex's lines. It fails on a major and minor version that matches none in the row. When the version cannot be read, it passes and says so. OpenCode's version stays on the `opencode server:` line.
- **`tiles doctor`.** Each harness's row gives its version and the newest one Tiles was proved on, such as `1.2.0 (proved on 1.4.0)`.
- On the development Mac, `claude --version` answers in 0.03 s, `pi` in 0.64 s, `codex` in 0.84 s and `opencode` in 1.05 s. Each runs while the terminal is asked and the engine loads.

### The network rule

`api.github.com` and `github.com` join `DOCUMENTED_HOST` in `scripts/check-network-owners.py` with no wildcard. Its `HOST_OWNERS` lets only `crates/tiles-cli/src/update.rs` name them, and `scripts/test_policy_scripts.py` refuses them in any other file and refuses look-alikes such as `api.github.com.evil.test`, `objects.githubusercontent.com` and `x.api.github.com`. `tiles-cli` reaches the network only through `tiles-net`. `tiles update` also runs `gh`, which connects to GitHub as the user's own sign-in, only when the user runs the command.

## Consequences

- Until the releases repository is public, the daily check sends one request a day that GitHub answers with 404, so no notice shows. `tiles update` through `gh` works today. The notice starts working, with no new build, once `RELEASES_REPO`'s repository, or the one `TILES_RELEASES_REPO` names, is public.
- A user who runs `tiles run` at least once a day sends GitHub one request a day; `TILES_UPDATE_CHECK=off` stops it. Each `tiles run` also starts the harness once more, for its `--version`. A fake harness in tests that ignored its arguments now answers `--version`, since the question would otherwise run its whole script.
- The first `tiles run` of the day can start up to 2.25 s later when GitHub is slow. Every later run that day reads the state file only.
- A harness release with a new minor version fails a `tiles check` line until a maintainer proves Tiles on it and adds it to the row; on Claude Code's 2.1.x patch releases nothing changes.
- Tests: `crates/tiles-cli/src/update/tests.rs` (the download through a fake `gh` and a fake releases directory, a tampered sum or archive refused with nothing replaced, the rename, the quarantine strip, the downgrade rule, the steps by hand, the once-a-day gate and its off switch, the notice and doctor line through the hostile corpus); `crates/tiles-cli/tests/update.rs` (the same through the binary with the fake `gh` first on `PATH`, macOS only); `crates/tiles-cli/src/proved.rs` (the table and each comparison); `each_harness_version_gets_a_line_after_its_harness` in `crates/tiles-cli/src/check.rs`; `the_rows_name_each_version_and_the_update_check_has_a_line` in `crates/tiles-cli/src/doctor.rs`; `a_dry_run_names_an_unproved_harness_version_and_nothing_else` and `the_version_line_shows_again_after_the_harness_exits` in `crates/tiles-cli/tests/run.rs`; the releases location in `scripts/test_install.sh`; `a_get_sends_the_host_user_agent_and_accept_only` in `crates/tiles-net/src/lib.rs`; the GitHub host cases in `scripts/test_policy_scripts.py`.
- Related: [ADR-011](ADR-011-surfaces-v0-1.md), [ADR-022](ADR-022-sealed-assets-and-releases-only-channel.md), [ADR-024](ADR-024-security-baseline-in-ci.md), [ADR-028](ADR-028-keep-the-model-out-of-the-cache.md), [ADR-029](ADR-029-opencode-launcher-standalone.md), [ADR-031](ADR-031-warehouse-sources.md).

Sources, checked 2026-10-19 from the development Mac: `gh api repos/<releases repository>/releases/latest` returned `tag_name` `v0.1.4`, `draft` false and `prerelease` false; the same `GET` sent anonymously with `User-Agent: tiles/0.1.4` and `Accept: application/json` got 404, the same request for the public cli/cli got 200, and one without a user agent got 403; a public release asset's `browser_download_url` (cli/cli v2.102.0) answered 302 to `release-assets.githubusercontent.com`; `gh release download --help` of gh 2.86.0 for `--dir`, `--pattern` and `--repo`.
