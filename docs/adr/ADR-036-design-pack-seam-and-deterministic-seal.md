# ADR-036: A build takes the design tokens sealed in a pinned design pack, the seal's seed comes from the plaintext so every build reproduces byte for byte, and the themes are the tokens' list

- Status: Accepted; supersedes [ADR-022](ADR-022-sealed-assets-and-releases-only-channel.md)'s seed drawn from `/dev/urandom` for each build and its consequence that release binaries are not reproducible; extends [ADR-021](ADR-021-obsidian-default-and-theme-switch.md)'s colour checks from Obsidian to every theme the build carries; its list of the three house greys in `themes.rs` is superseded by [ADR-037](ADR-037-plain-theme-for-builds-from-source.md), and the three greys under 3:1 by [ADR-042](ADR-042-house-greys-meet-three-to-one.md); its Tiles Design Licence line for a build from source and the placeholder wording of `tiles --licence` are superseded by [ADR-040](ADR-040-licence-cla-and-trademark-files.md)
- Date: 2026-10-20

## Context

The owner decided on 2026-10-19 to split Tiles into open and closed parts. The terminal product, the harness add-ons, the MCP server and the engine code are to be published, while the design system (the tokens, the Obsidian theme and the tuned light and dark themes, the playbook values and the goldens drawn with them) stays private and is sealed into builds. The official binary carries the sealed house design; a build from the published source gets a plain theme.

Before this record, `crates/tiles-engine/build.rs` read `assets/tokens.json` and `assets/forms/*.json` from the source tree and sealed them under a seed drawn from `/dev/urandom` for each build ([ADR-022](ADR-022-sealed-assets-and-releases-only-channel.md)). That has two problems for the split. The house tokens would have to sit in the public tree for the official build to embed them, and two builds of one tag embedded different bytes, so nobody could check that an official binary is a given tag plus a given design.

## Decision

- **The design pack.** A design pack is one file, `tiles-design-<n>.pack`: a text manifest (the format version, the pack number `n`, the two seed halves in hex, and each asset's path and size) followed by each asset's sealed bytes. It carries `tokens.json` alone: the forms are public, so they stay in the source tree. `crates/tiles-engine/src/pack.rs` reads and writes the format; the build script includes it, as it includes `chacha.rs`.
- **A deterministic seed.** The seed is two SHA-256 digests over one digest of a fixed constant and every asset's path and bytes, so sealing the same files gives the same bytes every time. SHA-256 is about 90 lines of our own (`src/sha256.rs`), checked against FIPS 180-4's examples, so the seal still adds no dependency. Each asset's nonce still comes from its path (ADR-022).
- **The seam.** With `TILES_DESIGN_PACK=<file>` set, `build.rs` hashes the file and refuses it, with one line naming both hashes, unless `scripts/design-pack.sha256` pins that hash for the file's name (the pattern of `scripts/skia-binaries.sha256`, [ADR-014](ADR-014-release-integrity.md)). It refuses a pack whose manifest is malformed, names an asset other than `tokens.json`, or holds tokens that do not open. It then embeds the pack's seed and sealed tokens as they are, and seals the forms in `assets/forms/` under the pack's seed. Without the variable, `build.rs` seals `assets/` under the seed derived from it. Either way a build embeds the same bytes for the same inputs, and the engine's `TILES_SEAL_SOURCE` says which kind it was.
- **The pack tool.** `cargo run -p tiles-design -- pack --tokens <tokens.json> --number <n> --out <dir>` checks that the tokens parse, writes the pack and prints its pin line. It calls `tiles_engine::pack`, so the tool and the build share one format and one seal. `crates/tiles-design` is the stub of the tool that moves to the private design repository at the split; the house `tokens.json` stays where it is until then. The CI `release-binary` job and the release job build pack 1 from the house `tokens.json` and build `tiles` with it. A test seals the house tokens and fails, printing the new line, when `scripts/design-pack.sha256` does not pin the result, so a token change re-pins the pack in the same PR.

- **Themes are a list.** `tokens.json` holds `themes.default` and `themes.list`; each theme has a `name`, an `about` (the few words `tiles theme` prints) and its colours. `tiles_engine::Theme` is a handle into the build's list, read once from the tokens the engine loads, and `Theme::default()` is the tokens' default. `--theme`, `TILES_THEME`, `tiles theme` and the `tiles_theme` tool take any name in the list, and their messages list the build's names. The engine refuses tokens with no theme or more than 16, a name that is not 1 to 24 lowercase letters, digits and dashes, a name listed twice, or a default not in the list. The house tokens list Obsidian, light and dark, with Obsidian the default, so [ADR-021](ADR-021-obsidian-default-and-theme-switch.md) holds unchanged. Whether a card's window is light comes from its card colour.
- **The colour checks cover every theme.** `crates/tiles-engine/tests/themes.rs` runs the contrast and colour-blind checks over every theme the build carries, not Obsidian alone. Three house categorical colours stand under 3:1 on their card: light `cat_3` (2.55:1) and `cat_5` (1.65:1) and dark `cat_5` (2.19:1), the greys playbook K6 puts third and fifth. The test lists exactly those three by theme, `cat_` number and colour, so a theme of the same name in other colours, as the plain theme to come, meets 3:1 with no exemption. It fails when one of the three passes, so a design change that lifts one also drops it from the list.
- **The release check reads the pack.** `scripts/check-release-binary.py --pack <file>` opens the pack itself, with ChaCha20 checked against the RFC's vector, and takes its colour, text and key needles from the pack's `tokens.json` and the tree's forms, the same set the build sealed. CI and the release job pass the pack they built.
- **Licence notices.** `tiles --licence` prints three lines: FSL-1.1-ALv2 for the code, the Tiles Design Licence for the design assets (naming the pack when the build took one), and the SIL Open Font License for Inter. The first two are placeholders until the licence texts are written.

## Consequences

- Two builds of one tree, or of one tag and one pack, embed the same sealed bytes. A test checks the build's embedded bytes against a fresh seal of `assets/`, and another seals a pack twice. Build provenance can now reproduce an official binary's assets from the public tag and the pinned pack hash.
- The seed is still in the binary and the derivation in the source, as ADR-022 says; with the source public, the seal stops `strings` and a JSON scan, and the licence forbids the rest. A seed that depends only on the plaintext means two builds of the same design share a key; that reveals nothing the binary does not already hold.
- Any change to the house `tokens.json` changes pack 1's hash, so it also updates `scripts/design-pack.sha256`, or the `tiles-design` test and the `release-binary` job fail.
- `tiles_engine::Theme` is no longer an enum: code that named `Theme::Light` looks the theme up by name, since a build carries the themes its tokens list. The light and dark themes keep their names in both the house tokens and the plain theme to come.
