# ADR-021: Obsidian is the default theme, and `/theme` switches themes, earlier cards included where kitty allows

- Status: Accepted; how `tiles open` draws a card in a plain shell is superseded by [ADR-023](ADR-023-open-in-a-window.md); since [ADR-024](ADR-024-security-baseline-in-ci.md) sets `TILES_SESSION` wherever the wrapper runs, a theme change swaps cards in place only where `TILES_FRAMES` is set too; saving the rows fetched from Omni in `<id>.call.json` is superseded by [ADR-027](ADR-027-omni-rows-stay-in-memory.md), which keeps them in the memory of the session that fetched them; Obsidian's six categorical colours are superseded by [ADR-047](ADR-047-context-greys-and-no-red-category.md), which drops its orange and red and lists five
- Date: 2026-10-18

## Context

Tiles drew in light or dark, and `tiles run` picked between them from the terminal's background. The owner had a dark theme named Obsidian from an earlier, private design project: near-black page, graphite tiles, white-alpha hairlines, a purple accent, yellow and green. Part 1 of this work ported it into `tokens.json` with a port script kept with the house design, so no Obsidian hex is typed by hand. The owner saw a KPI scorecard and a line chart in Obsidian beside dark and decided, 18 Oct 2026, to make Obsidian the default, with a command such as `/theme` to switch at any time. The owner then asked that cards already drawn change too: "if a user already generated tiles in a theme, would then changing the theme allow them to have the already rendered theme into the new selected one too?"

## Decision

- **Obsidian is the default.** A card is drawn in, first to last: its own `--theme` (`tiles render`), `TILES_THEME` for a session, the saved theme, then Obsidian. `Theme::default()` and `Options::default()` are Obsidian. `tiles run` no longer picks light or dark from the terminal's background; it passes a `TILES_THEME` the user set and nothing else, so the server reads the saved theme on every card. Light and dark stay.
- **The choice is saved locally.** `tiles theme` lists the themes with the one in force marked and where it came from; `tiles theme <name>` saves it in `config.json` under `$TILES_CONFIG_DIR`, else `$XDG_CONFIG_HOME/tiles` or `~/.config/tiles`. The file is owner-only, written through a fresh temporary file renamed into place, and keeps any other keys. Nothing in it leaves the machine.
- **`/theme` inside the harnesses.** The MCP server gains a `tiles_theme` tool (optional `name`: `obsidian`, `light` or `dark`) and a `theme` prompt that asks the model to call it. `tiles_theme` writes only the settings file and redraws cards from the cache. It never reaches the network, so it is pre-approved wherever `tiles_chart` is. Each harness's own `/theme` decides what the user types. Its own source was read for this (versions below):
  - Claude Code 2.1.302 owns `/theme` (its colour theme) and matches a built-in name before any other. Tiles offers `/mcp__tiles__theme [name]`, Claude Code's command for an MCP prompt, in every session. When the Claude plugin loads (kitty and Ghostty) it also offers `/tiles:theme` from `adapters/claude/commands/theme.md`.
  - OpenCode 1.19.3 has `/themes` and no `/theme`, so Tiles' config layer adds a `theme` command under `command`, through `OPENCODE_CONFIG_CONTENT` for `tiles run` and Tiles' own `config.json` for `tiles install`. OpenCode also lists the MCP prompt as `/tiles:theme`, but it always fetches a prompt with the literal `$1`, `$2` and so on as argument values and fills in what the user typed afterwards. The `theme` prompt accepts only a theme name or nothing, so it refuses `$1`, and `/tiles:theme` fails in OpenCode with or without a name. OpenCode users use `/theme`.
  - Pi 1.0.0 has no `/theme` (`dist/core/slash-commands.js`) and no MCP server under Tiles, so the Pi extension registers `/theme [name]` with `registerCommand`. It runs `tiles theme [name]` and shows what that prints with `ctx.ui.notify`, with no model call.
  - Codex 0.163.0 owns `/theme` (syntax highlighting) and has neither custom prompts nor MCP prompts. `tiles install codex` writes the skill `tiles-theme` to `$CODEX_HOME/skills/`, offered as `$tiles-theme` and in `/skills`. `tiles run codex` adds nothing, since no `-c` key adds a skill, and the model calls `tiles_theme` when asked in words.
- **Earlier cards change where kitty can swap them in place.** Each card now saves its call beside it as `<id>.call.json`: the tool's arguments, the rows fetched from Omni for it and the geometry it was drawn at. Inside a `tiles run` kitty session (the one that sets `TILES_SESSION`, ADR-017), setting a theme draws every card that session made again in the new theme under the same id and the same cells. The picture is written first and then the geometry, which records the theme and no entrance. The wrapper notices the geometry changed and sends the new picture under the card's image id with its virtual placement, so every placeholder copy on screen and in scrollback shows it, with no new placement and no duplicate. A card mid-entrance is swapped once it settles.
- **Elsewhere only new cards change.** Warp keeps every picture it was sent, herdr re-sends leave stale copies, and the sixel and text routes have no image id to replace. There the result says that cards on screen keep their theme and `tiles open <id>` shows an earlier card in the new theme: it draws the saved call again as a new card in the theme in force. Inside `tiles run` it prints what the chart tool would; in a plain shell, where `TILES_DRAW` is unset, it prints the new card's id, theme and PNG path. Cards from earlier sessions are never touched.
- **A chart one theme draws, every theme draws.** Obsidian's categorical palette has six colours and light and dark have five, from the gallery (playbook K6). The source design allows six per tile, but light and dark have no sixth gallery colour to add, so the series limit is the shortest palette of any theme: five. `Palette::series` holds it, colours past it stay unused, and a sixth series is refused in every theme with the same message. A longer palette in every theme raises the limit with no code change.
- **Obsidian is checked as its source design checks it.** `crates/tiles-engine/tests/themes.rs` holds Obsidian's six categorical colours to at least 3:1 on the card, matching the source design's "Needs labels: none". It holds the accent and the bad red to 3:1 and ink and muted text to 4.5:1. Every two categorical colours must stay at least 10 apart in CIEDE2000 under deuteranopia and protanopia, simulated as the source design's specimen script does with Machado, Oliveira and Fernandes (2009) at severity 1. The pairs the source design flags measure 8.0 to 9.5, and Obsidian's closest pair, orange and red with deuteranopia, measures 11.4. Every form has an Obsidian golden beside its light and dark ones.

## Consequences

- A user on a light terminal now gets dark Obsidian cards until they run `tiles theme light`; the background is no longer read for the theme.
- The cache holds each card's call, the rows fetched from Omni included, beside its picture, owner-only and pruned with the card. The picture already shows those values; nothing new leaves the machine (ADR-013).
- A theme change inside a kitty session redraws every card of the session in turn, about as long as drawing each again; cards drawn before this change have no saved call and keep their theme.
- The gallery prototype has no Obsidian card, so `tests/reference.rs` measures light and dark only; Obsidian's baselines are its goldens.
