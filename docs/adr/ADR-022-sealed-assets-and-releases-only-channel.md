# ADR-022: The forms and tokens ship sealed, release binaries carry no source path, users install from a releases-only repository, and releases are signed once the Apple secrets exist

- Status: Accepted; the seed drawn fresh for each build is superseded by [ADR-036](ADR-036-design-pack-seam-and-deterministic-seal.md), which derives it from the plaintext and lets a build take the tokens from a pinned design pack; `scripts/install.sh`'s download with `gh` is superseded by [ADR-038](ADR-038-open-core-split.md), which downloads with curl; the releases token's power to replace a release and its `SHA256SUMS` together is closed for `install.sh` by [ADR-056](ADR-056-signed-sums-and-weekly-advisories.md), which signs `SHA256SUMS` with a key held in the release workflow's secrets; its releases-only repository is superseded by [ADR-059](ADR-059-public-cut.md), which publishes to this repository's own releases
- Date: 2026-10-18

## Context

[ADR-019](ADR-019-copying-without-company-data.md) named two gaps in Tiles' copy protection. Installing downloaded the release from the private source repository, so every installer needed read access to the source. And the forms and design tokens, the Obsidian theme among them ([ADR-021](ADR-021-obsidian-default-and-theme-switch.md)), shipped as plain JSON inside the binary ([ADR-010](ADR-010-engine-v0-1.md): "embedded with `include_str!`").

The release binary built from `main` at `6cc92eb` showed both, and more. `strings` printed 183 home-directory paths (each dependency's source path in the build machine's cargo registry), 21 Tiles source paths such as `crates/tiles-cli/src/harness.rs`, the token JSON with its keys (`"categorical"`) and colours, and every form's summary and role notes. `scripts/check-release-binary.py` found 96 asset keys written as JSON, 39 asset colours and 43 form texts in that binary.

The owner, 2026-10-18: "we want it 1. secure and private to the point no one can copy our chart intelligence ... or copy our engine or anything so this novel tech remains ours."

## Decision

- **Sealed assets.** `crates/tiles-engine/build.rs` encrypts `assets/tokens.json` and every `assets/forms/*.json` with ChaCha20 (RFC 8439) into the build's `OUT_DIR`, and the engine includes only those sealed bytes. The key is never stored: the build draws two 256-bit seed halves from `/dev/urandom` for each build, and `src/chacha.rs` derives the key from them as one ChaCha20 block over the mixed halves, at build time to seal and at load to open (`src/seal.rs`). Each asset's nonce comes from its path. The cipher is about 80 lines of our own, checked against the RFC's test vector, so the seal adds no dependency. The plain JSON exists only in the process's memory while it parses; it never touches the user's disk. A debug build still reads `$TILES_DEV_ASSETS` from disk when set. This supersedes ADR-010's "Both are embedded with `include_str!`".
- **Release builds.** The release profile has no debug info (`debug = false`), strips symbols, and keeps thin LTO and one codegen unit. The release job builds with the flags `scripts/release-rustflags.sh` prints, which remap every path rustc would write into the binary for panic locations: the home directory to `~`, the cargo home to `/cargo`, the registry's sources to `/deps`, the checkout to `/tiles`, and each Tiles source file to `tiles/<n>`. `sh scripts/release-rustflags.sh --map`, run at a release's tag, says which file `tiles/<n>` is.
- **The check.** `scripts/check-release-binary.py` scans the raw bytes of a release binary, a superset of what `strings` prints, and fails on a home directory path, a cargo registry path, a Tiles crate's source path, the checkout's path, any colour from the assets, any form text of 16 or more characters, or any asset key written as a JSON key. It reads its needles from the asset files, so a new colour, key or form is covered without editing the script. It runs in the release job, where it stops the release, and in the CI job `release-binary`, which builds the release binary on Linux for every PR. `scripts/test_policy_scripts.py` checks that it catches each kind of leak.
- **A releases-only channel.** Releases go to a private repository that holds only release files: the tarballs, `SHA256SUMS` and `scripts/install.sh` (`RELEASES_REPO` in `crates/tiles-cli/src/update.rs` names it). The maintainer gives each user read access to that repository alone, so installing never needs access to the source. `scripts/install.sh` downloads from it, with curl over HTTPS since [ADR-038](ADR-038-open-core-split.md), and checks the tarball against `SHA256SUMS` as before. The publish job writes there with a secret holding a fine-grained token that can write only to the releases repository, so this repository's own workflow token is read-only in every release job. A `preflight` job fails the release in seconds until that secret exists. This supersedes [ADR-007](ADR-007-stack-and-delivery.md)'s install from the private repository and moves [ADR-014](ADR-014-release-integrity.md)'s publish step to the releases repository; ADR-014's hash chain holds unchanged.
- **Signing and notarisation.** A `sign` job runs between the builds and the publish job on macOS. It runs no dependency code, so the Apple secrets live there and in no build job. It checks each tarball against its build job's hash, signs `tiles` with the Developer ID certificate (hardened runtime, secure timestamp), notarises it with `notarytool`, and hashes the signed tarball for the publish job to check (`scripts/sign-macos.sh`). With none of the six Apple secrets set, it passes the tarballs through unsigned with a warning; with only some set, it fails. This supersedes ADR-007's "signing and notarization come with public distribution".
- **Licence.** `LICENSE` now also forbids reverse engineering, decompiling, disassembling or decrypting Tiles, extracting the forms, tokens or chart rules it embeds, circumventing the seal, and training a model on its output to reproduce how it chooses or draws charts, except where law expressly permits it.
- ADR-019's list of the layers that hold today is updated to match this record.

## Setting up the channel and signing

The maintainer creates the releases repository, the write token for it and the six Apple secrets once on GitHub; nothing in this repository creates them. The secret names are those `.github/workflows/release.yml` and `scripts/sign-macos.sh` read. The Apple secrets are added all together or not at all.

## Consequences

- The seal stops `strings`, a JSON scan and casual extraction. It is not secrecy against someone who disassembles `tiles`: the seed halves and the derivation are in the binary, and the opened assets sit in memory while it runs. The licence makes that unlawful. Token and form key names still appear as bare words where serde reads them, since they are the code's own field names; their values, the JSON and the form texts do not.
- A new form file is sealed by the build script automatically; it still joins `forms::EMBEDDED` by hand.
- Two builds of the same commit seal with different keys, so release binaries are not byte-for-byte reproducible. Build provenance, when it comes (ADR-014), attests the build rather than reproducing it.
- A panic in a release names `tiles/<n>` instead of a file; `--map` at the tag reads it.
- Every PR pays for one more build, the Linux release build in `release-binary`.
- No release publishes until the maintainer creates the releases repository and its token. Releases ship unsigned, as before, until the Apple secrets exist; after that, a browser download passes Gatekeeper without removing the quarantine flag.
- The releases token is long-lived and can write releases to the releases repository; whoever holds it can replace a release and its `SHA256SUMS` together, as ADR-014 notes for the publish job. It expires within a year and is rotated then.
