# ADR-069: After `tiles setup`, a harness typed at a zsh, bash or fish prompt starts through `tiles run`

- Status: Accepted; amends [ADR-011](ADR-011-surfaces-v0-1.md), whose front door was a `tiles run` typed per session, [ADR-035](ADR-035-macos-package-and-tiles-setup.md), whose `tiles setup` changed only the harnesses, and [ADR-060](ADR-060-setup-prints-a-step-list.md), whose step list gains a `Shell` step and whose closing line changes when the shell is wired
- Date: 2026-11-27

## Context

Only `tiles run <harness>` drew the card inline. `tiles setup` registered the MCP server with each harness, but outside `tiles run` no wrapper draws, so an installed Claude Code, Codex or OpenCode answered with a short summary and the card's PNG path (`install::installed_draw`: Pi draws its own image, every other harness gets the text route), and an installed session had no companion window either. People install once and then type `claude`, `codex`, `opencode` or `pi` as they always do; they do not type `tiles run` first.

Three ways to close the gap were weighed:

- **A persistent Claude Code plugin.** The mod already draws in kitty and Ghostty under `tiles run`. Registered for good it would cover one harness in two terminals; Codex, OpenCode, Warp, WezTerm, VS Code and iTerm2 still need the wrapper, which only `tiles run` starts.
- **A `claude` shim first on `PATH`.** It would cover every harness, but putting a directory ahead of the user's own on `PATH` needs the same startup-file edit as a shell function, shadows the harness for scripts and other programs too, and a stale shim breaks the harness for everything.
- **A shell function per harness**, defined by a file `tiles setup` wires into the interactive shell once. Only an interactive prompt reads it, so scripts, `ssh host claude`, editors and other programs that start a harness are untouched, and the function can check for a terminal before it calls Tiles.

## Decision

- **What setup writes.** For zsh and bash, Tiles' own `shell.sh` in the Tiles config directory (`$TILES_CONFIG_DIR`, else `$XDG_CONFIG_HOME/tiles` or `~/.config/tiles`), and two lines at the end of each startup file it wires, after one newline: a comment beginning `# Added by tiles setup:`, and `if [ -r '<shell.sh>' ]; then . '<shell.sh>'; fi`, which leaves the shell's status at 0 when the file is gone. The startup files are `$ZDOTDIR/.zshrc` (or `~/.zshrc`) when zsh is the login shell or the file exists, and the `~/.bashrc` and `~/.bash_profile` that exist, or `~/.bashrc` when bash is the login shell and neither does. For fish, `$XDG_CONFIG_HOME/fish/conf.d/tiles.fish`, which fish reads by itself, so no file of the user's changes; it is written when fish is the login shell or its config directory exists. A startup file is appended to through the file, so a linked dotfile stays a link. `crate::shell` holds the scripts and the rules.
- **What the scripts do.** Each defines `claude`, `codex`, `opencode` and `pi` with `function name`, which an alias of the same name cannot break. The function runs `tiles run --from-shell <harness> "$@"` when standard input and output are both a terminal, `tiles` is on `PATH`, `TILES_PLAIN` and `TILES_RUN` are empty (no `tiles run` around this shell already); otherwise it runs the harness itself with `command`. `command claude` skips Tiles for one launch.
- **`tiles run --from-shell`.** A harness not on `PATH` gets `<name>: command not found` and status 127, as the shell would print it. Help and version flags, one-shot and scripted modes (`claude -p`, `--print`, `--output-format`, `--input-format`, `--bg`; `pi -p`, `--mode json` or `rpc`, `--export`, `--list-models`) and each subcommand that opens no conversation (`claude mcp`, `codex exec`, `opencode run` and the rest in `shell::steps_aside`, read from each harness's `--help`) replace `tiles` with the harness through `exec`, its arguments untouched. Codex's `resume` and `fork` and a prompt or project argument go through Tiles. Anything that fails before the harness starts (the cache, the terminal detection, the engine, the plan, the add-ons) prints one line ending `; starting <harness> without Tiles` and replaces `tiles` with the plain harness; a panic on the main thread before the start does the same from the panic hook. After the start, `tiles run` hands back the harness's exit status as before.
- **No wait.** `tiles run` from the shell takes the harness's version and the daily update notice only if they are already in, so neither the version probe nor the update check's two-second deadline holds up the harness. The update check keeps running and saves what it finds for the next launch.
- **Consent.** The shell is in setup's one question (`Set up Tiles for Claude Code and zsh?`), with a `Shell` step listed before it (`will wire zsh: claude, codex, opencode and pi typed in a new terminal tab start through tiles run`); `--dry-run --verbose` lists `write <shell.sh>` and `add 2 lines to the end of <file>`. A second run reads `Shell (already wired for zsh)` and changes nothing. A startup file whose Tiles lines were changed by hand is named and left. When the shell is wired, the closing line reads `Next: run tiles check, then open a new terminal tab and type <harness>.`.
- **Undo.** `tiles shell off` removes the two lines and the newline before them from each startup file that holds them, leaving every other byte as it was, deletes a startup file setup created that holds nothing else, and deletes `shell.sh` and `tiles.fish`. `--dry-run` says what it would do. `tiles shell` prints the same line as `tiles doctor`'s `shell:` row: wired for which shells through which files, or not wired.
- **One server per session.** After setup, Claude Code also has a user-scope `tiles` server. Claude Code 2.1.332, started with a user-scope stub server and a `--mcp-config` stub of the same name from a scratch `HOME`, started only the `--mcp-config` one, listed with `"source":"dynamic"`, so a session from the shell runs the session's server alone. Codex's `-c mcp_servers.tiles.*` and OpenCode's `OPENCODE_CONFIG_CONTENT` override the installed server's keys, and Pi's installed extension stands aside under `TILES_RUN`.

`crates/tiles-cli/src/shell/tests.rs` covers the plans per shell, the block's quoting, byte-for-byte undo over a file with and without a final newline, an empty file, CRLF lines, a missing file and a linked one, lines added after the block, hand-changed lines, and each harness's step-aside table. `crates/tiles-cli/src/setup/tests.rs` covers the `Shell` step through the question, a dry run and a second run. `crates/tiles-cli/tests/shell.rs` drives the binary: setup wires zsh, `tiles shell` and `tiles doctor` report it, `tiles shell off` gives the `.zshrc` back byte for byte, a one-shot use reaches a stub harness untouched, an interactive one starts with `-e <add-on>` and `TILES_RUN=1`, an unusable cache starts the harness plain with its exit status, and the written script run by zsh and bash with no terminal starts the harness plain.

## Consequences

- Plain `claude`, `codex`, `opencode` and `pi` in a new terminal tab get what `tiles run` gives: the card inline on every route where `tiles run` draws inline, and the companion window on the text route on macOS. `tiles run` stays for a terminal not wired, and for its own flags (`--wrapper`, `--terminal`, `--route`, `--allow-omni`).
- The installed servers stay: they serve a harness started by anything other than an interactive prompt, such as an editor or a script, on the text route as before.
- `tiles run` costs what it always did before the harness starts: the terminal query, the engine's first load and, for OpenCode, its `--help` (ADR-029). It no longer waits on the version probe or the update check from the shell.
- The step-aside lists are read from the `--help` of Claude Code 2.1.332, codex-cli 0.172.0, OpenCode 1.19.3 and Pi 1.0.0. A subcommand a later release adds runs through `tiles run` until its list is updated; harness version bumps (ADR-032) read `--help` and update `shell::steps_aside` with them.
- An alias that adds flags, such as `alias claude='claude --model opus'`, still reaches the function, flags and all, in zsh and bash. An alias that points `claude` at a file, as older Claude Code installers wrote (`alias claude=~/.claude/local/claude`), runs that file and skips Tiles; `tiles doctor` cannot see aliases.
- A shell other than zsh, bash or fish is not wired; `tiles doctor` says so, and `tiles run` still works there.
