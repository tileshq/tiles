# ADR-029: `tiles run opencode` gives the OpenCode launcher a private server with `--standalone`, and `tiles check` names the OpenCode it found

- Status: Accepted; amends [ADR-011](ADR-011-surfaces-v0-1.md)'s OpenCode row
- Date: 2026-10-19

## Context

On 2026-10-19 the owner tested Tiles v0.1.2 in Warp on a laptop whose OpenCode is a launcher build. Claude Code and Pi drew their cards. In OpenCode the first chart showed its 48 `[tile:eba3b4 NN/48]` rows as plain text, and the dashboard was refused three times with "the cards stack 123 rows tall in this terminal, over 99", then came back as two cards, 91247c (79 rows) and d15a9b (48 rows), both shown as text. `tiles check` printed the OpenCode cards as "48 rows" and "79 rows", with no "of N, at most M", so their server had no `TILES_ROWS`. The trace's session saw all three blocks whole and left them blank, since none carried its `TILES_SESSION` token ([ADR-017](ADR-017-early-card-and-entrance.md)). After `pkill -f opencode`, a fresh `tiles run opencode` listed none of the session's MCP servers, and the model drew an ASCII bar chart by hand.

Its `opencode --version` printed `opencode v2.0.32`, while sst/opencode's releases end at v1.19.3 (2026-10-16). That `opencode` is a launcher script, and its `--help` describes another CLI: `opencode <subcommand> [flags] [<directory>]`, with `--standalone` ("Run with a private server instead of the background service") and `--server string` ("Connect to a server URL instead of the background service"). By default its TUI attaches to a background service that was started earlier with its own configuration. `OPENCODE_CONFIG_CONTENT` and the MCP server's variables, set on the TUI's process, never reach that service. On the first try the service still held a tiles server from an earlier run, without the session's rows or token; after the `pkill` it held none. `tiles run opencode --standalone` then drew the signups card at the right size and the four-card dashboard, fitted, in the same OpenCode.

Read for this record: sst/opencode v1.19.3 `packages/opencode/src/config/config.ts`, 2026-10-19. For the launcher, only its `--help` and the laptop's retest were available.

## Decision

- **Tell the two CLIs apart by `--help`.** `tiles run opencode` runs `opencode --help` in a thread while it asks the terminal and loads the engine. Stdin is closed, the answer goes to an unlinked file, and the run waits at most 5 s. When the answer lists `--standalone`, it is the launcher. sst/opencode 1.19.3 has no such flag and answers in 0.8 s on the 2017 development Mac.
- **The launcher gets `--standalone`.** The plan puts `--standalone` before the user's own arguments unless they already pass it. A `--server` among them stops the launch with one line, since the server it names never loads the session's tiles server. sst/opencode's launch is unchanged. When `--help` does not answer, the launch is unchanged too, and `tiles check` fails its OpenCode line. `tiles run --dry-run opencode` prints the flag.
- **The session's config stays in `OPENCODE_CONFIG_CONTENT`.** Both CLIs read it once the TUI has a server of its own, which the laptop's retest showed for 2.0.32. Tiles does not also write the config to a file for `OPENCODE_CONFIG`, since a second channel would add nothing to the proved one.
- **A permanent install cannot shadow the session on sst/opencode.** OpenCode 1.19.3 loads the global `config.json`, `opencode.json` and `opencode.jsonc` (`config.ts:272-274`), then `OPENCODE_CONFIG` (`:415`), the project's files and `.opencode` directories, then `OPENCODE_CONFIG_CONTENT` (`:482-488`), each through remeda's `mergeDeep`, with `instructions` arrays joined. The session's `mcp.tiles` replaces an installed `mcp.tiles` key by key: its command, every environment variable the session sets, and `enabled`. A session-specific server name, and disabling the installed server, are not needed. 1.19.3 reads `config.json` (`:272`), so `tiles install opencode` writing that file is not a second defect there.
- **`tiles check` and `tiles doctor` name the OpenCode they found.** The `opencode server:` line gives the version from `opencode --version`, which CLI it is, which server a `tiles run` session's model calls, and the version Tiles was proved on (1.19.3 for sst/opencode, 2.0.32 for the launcher). It fails on another major version or a `--help` that did not answer, so the next jump shows before a laptop test. That failure on a major version Tiles was not proved on is the early warning the owner asked for, automatic checks on harness updates: on each new harness release a maintainer re-proves Tiles and bumps the two proved versions, `PROVED_PUBLIC` and `PROVED_LAUNCHER` in `crates/tiles-cli/src/opencode.rs`. When `~/.config/opencode/config.json` holds a tiles server, an `opencode install:` line passes on sst/opencode, by the merge order above, and fails on the launcher, where it is not proved which of the two its private server keeps. `tiles doctor` prints the same sentence under OpenCode's row.
- **The trace line names another session's cards.** When the last session in the trace made no card but saw saved cards whole, the `trace:` line names them and says the harness did not call this session's tiles server.
- **The dashboard refusal stays.** The 123-row refusal came from the service's stale tiles server, which had no `TILES_ROWS`. The size matches a server that reads Warp's 8x16-point cell as device pixels, the rule before [ADR-025](ADR-025-warp-cell-size-rows-and-laptop-check.md), which doubles a card's rows: the test dashboard stacks over 99 rows that way at 108 columns. With the session's rows, `card::draw` already fits the picture to the rows before the 99-row refusal. A server that does not know the rows keeps refusing, since on the sixel route a picture shows at its pixel size and a fitted one would spill past its block.

## Consequences

- In the launcher, a `tiles run` session runs on a private server of its own, not the background service. Which of the service's features that leaves out is not known; its `--help` says only "Run with a private server instead of the background service".
- A Tiles session cannot share the launcher's background service: the service loaded its configuration when it started, and nothing in a TUI's environment reaches it, so a per-session tiles server cannot be guaranteed there.
- On sst/opencode with a permanent install, the installed instruction file loads beside the session's, since OpenCode joins `instructions` arrays. The installed one describes the text route and the session's the block. The result the tool returns is the session's either way.
- Each `tiles run opencode` start spends up to the `--help` answer's time, overlapped with the terminal query and the engine load. A future sst/opencode that adds a `--standalone` flag would be read as the launcher; the `opencode server:` line names the CLI, so that shows.
