# Install and doctor

`tiles install <harness>` adds Tiles to a harness for sessions started without `tiles run`; `tiles setup` runs those installs for every harness on `PATH` after one question (ADR-035); `tiles doctor` reports the terminal, route, harnesses with their versions, card folder, Omni setup and the update check with no secret; `tiles update` installs a newer release (ADR-032); `tiles check` prints a pass or fail line per check of how cards draw in this terminal (ADR-025); `scripts/install.sh` installs the release binary on a Mac, and `scripts/package-macos.sh` builds the one `.pkg` a release ships (ADR-035).

## Sub-features

- `install-dry` lists the steps without doing them.
- `setup`: `tiles setup` prints `Tiles found:` (the terminal, one line per other `tiles` on `PATH` with its version, one line per harness: `not on PATH`, `<path>, already set up`, `<path>, not set up`, `not set up; Tiles leaves it: <tiles install's refusal>`, or for Claude Code with a user-scope `tiles` server for another binary `<path>, set up with another tiles, <command>; Tiles will replace it`, with `claude: run claude mcp remove tiles --scope user` before the `claude mcp add` step (ADR-039), and for one in a project's or folder's config `..., in Claude Code's project config; Tiles leaves it: run claude mcp remove tiles --scope project, then tiles setup`, then an `omni:` line), then `Tiles will change:` with each install step and `Set up Tiles for <harnesses>? [y/N]`. Only `y` or `yes` installs; no answer, end of input or anything else prints `Nothing changed.`. `--dry-run` prints `Dry run: nothing changed.` and asks nothing; `--yes` asks nothing; `-y` is refused. With nothing to change it asks nothing and says so: `Nothing for Tiles to change; see the lines above.` when a harness is refused or its `tiles` server is left. A failed `claude mcp remove` prints `Claude Code keeps its old tiles server: run claude mcp remove tiles --scope user, then tiles setup` and runs no `mcp add`. Then `To finish the data sources, run:` with `tiles omni set-key https://<host>` and `Then run tiles setup again, ...`. Omni's key is never read: only `TILES_OMNI_URL`, whether `TILES_OMNI_API_KEY` is set, the Keychain's `url` item and whether a key item exists. Covered by `crates/tiles-cli/src/setup/tests.rs` and `crates/tiles-cli/tests/setup.rs` (stub harnesses, temp `HOME`).
- `old-copy`: each other `tiles` on `PATH` gets a `Tiles found:` line, `tiles: <path>, version <v>` (or `which printed no version`, after at most 5 s) then `comes first on PATH, so a terminal runs it, not this one (<this>, version <v>)`, `is also ahead of this one on PATH`, `is later on PATH than this one`, or `is on PATH, and this one (<this>) is not`; a symlink or hard link to the running one is not a copy. One ahead that is newer or the same version reads `is newer than this one (<this>, version <v>) and comes first on PATH, so a terminal runs it` (or `the same version as`) and is never offered a move. One ahead that is older, or whose version cannot be read (a development build counts as unreadable), and that the user owns: in a terminal it is listed as `tiles: move <path> aside, to tiles-<version>-old beside it` under `Tiles will change:` (with no install to make, the line after reads `Tiles changes no harness; see the lines above.` when a harness is left, and a declined harness question prints `No harness changed.` in place of `Nothing changed.`), and setup asks `Move <path> aside, to <new path>? [y/N]` after the harness question, and on `y` renames it (never deletes) and prints `Moved ... To run <this> as tiles, open a new terminal tab, or run hash -r (rehash in zsh).`. Without a terminal, with `--yes` or `--dry-run` the move is not listed and setup prints `To move <path> aside, run: mv -n <path> <new path>, then ...`; after `n` it prints the same `mv -n`; a copy of another user's ends `it is not yours, so Tiles leaves it: sudo mv -n ...`. `tiles doctor` prints one line per copy ahead, under its version line, an older one ending `move it aside: mv -n <path> <new path>` (ADR-035, 2026-10-21). Covered by `crates/tiles-cli/src/copies.rs` (with a running version of 0.1.9), `crates/tiles-cli/src/setup/tests.rs` and `an_older_tiles_ahead_on_path_is_named_and_without_a_terminal_left_with_its_mv` in `crates/tiles-cli/tests/setup.rs`, all with fake `PATH` directories.
- `doctor-setup`: with a harness on `PATH` not set up as `tiles setup` would set it up, `tiles doctor` prints `  setup: Tiles is not set up, or is out of date, for <harnesses>; run tiles setup` after the harness rows, and for a Claude Code server for another `tiles` `  setup: Claude Code is set up with another tiles, <command>; run tiles setup to replace it`, and doctor changes nothing (`a_harness_on_path_without_tiles_set_up_is_offered_tiles_setup` in `doctor.rs`). It never runs `claude mcp get`: Claude Code's registration is a hint read from `~/.claude.json` (`mcpServers.tiles`), and a missing file or one of another shape leaves Claude Code out (`doctor_reads_claude_codes_config_and_starts_no_server` in `tests/setup.rs`); `tiles setup` decides through `claude mcp get`.
- `cache-clear`: `tiles cache clear` removes every card, call and entrance frame, prints `Removed N cards.` (`1 card`), and leaves `run/` alone; any other argument prints `tiles: usage: tiles cache clear` and exits 2; `tiles doctor` afterwards reads `(0 saved)` (`crates/tiles-cli/tests/cache.rs`, ADR-028).
- `install-pi` writes `~/.pi/agent/extensions/tiles/index.ts` and `tool.json`.
- `install-opencode` writes `~/.config/opencode/config.json` and `tiles-instructions.md`, and refuses a `config.json` of the user's own.
- `install-claude`, `install-codex` run the harness's own `mcp add`; with Omni configured `install-codex` then adds `default_tools_approval_mode = "prompt"` to Codex's `[mcp_servers.tiles]`, and refuses an approval mode of the user's own there.
- `doctor` prints one block of lines; under the `opencode` row, when it is on `PATH`, one more line with the sentence `check`'s `opencode server:` line prints, whole (`opencode_is_reported_with_its_version_and_server` in `doctor.rs`, ADR-029); the Omni key only as "API key set", with where it came from (the environment or the Keychain). With Omni configured, a `  warning:` line follows for each install that still runs a Tiles tool unasked (OpenCode's Tiles `config.json` with `tiles_chart` or `tiles_theme` at `allow` or an Omni tool unlisted, a Codex tiles server with no `default_tools_approval_mode`), ending in `run tiles install <harness>`.
- `check` prints only lines starting `pass ` or `fail `, exits 1 when any fails, and shows the version against `--tag`, the terminal and route, the graphics answer, the cell size with its two candidates, `TILES_ROWS` on the pre-cut route, who draws per harness on `PATH`, the OpenCode version with its CLI (sst/opencode or a launcher with a background service), the server a `tiles run opencode` session's model calls and the version Tiles was proved on (failing on another major version), an `opencode install:` line when `~/.config/opencode/config.json` holds a tiles server, the theme in use, the card cache, the newest five cards' theme, tone and rows, and, when `TILES_TRACE` names a file, whether its last session saw every card whole, naming any cards it saw whole that another session's server made. Never a card's title or row values. Piped from a shell (`tiles check --tag v0.1.1 | tee check.txt`), with one of stdin and stdout a terminal, it and `tiles doctor` ask `/dev/tty` for the terminal's answers and size, so the report matches an unpiped run; with neither a terminal, as when an agent runs it, they ask no terminal; either way, when nothing could be asked, the `graphics:` and `answers:` lines say `not asked` and why (ADR-054; `with_no_terminal_to_ask_the_graphics_line_names_dev_tty` in `check.rs`, `a_probe_with_no_terminal_names_dev_tty_and_why` and `dev_tty_is_asked_only_beside_a_terminal` in `wrap/mod.rs`).
- `doctor-versions`: each harness row reads `<name> <path>  <version> (proved on <the newest version in its row>)  <install state>`, `version unknown` when `--version` gave none; an `update check:` line before `network:` names `TILES_UPDATE_CHECK` as read, how long ago the last check ran (`3 h ago`) and the newest release seen, `off` with `TILES_UPDATE_CHECK` set to `off`, `0`, `false` or `no`, that it does not run when `TILES_RELEASES_REPO` is not `<owner>/<repo>`, and `none for a build that carries no release tag (0.0.0)` in a development build; when a newer release was seen, `Tiles vX.Y.Z is available; run tiles update` follows the first line (`the_rows_name_each_version_and_the_update_check_has_a_line` in `doctor.rs`, ADR-032).
- `check-versions`: after the line for Pi, Claude Code or Codex, a `<name> version:` line that fails on a major and minor version matching none Tiles was proved on (Pi's row holds 1.0.0, 1.2.0, 1.3.0 and 1.4.0) and passes with `could not be read` when `--version` names none (`each_harness_version_gets_a_line_after_its_harness` in `check.rs`).
- `update`: `tiles update` downloads through `gh` when signed in, else from `TILES_ARCHIVE` and `TILES_SUMS`, else prints the steps by hand and exits 1; checks `SHA256SUMS` and refuses a mismatch with nothing replaced; removes the quarantine flag; writes the binary beside `$TILES_BIN_DIR/tiles` (default `~/.local/bin/tiles`), runs its `--version` and renames it over; prints `updated tiles from <old> to <new> at <path>`; refuses an older release without `--allow-older`; `--check` only reports. Covered against a fake `gh` and releases directory by `crates/tiles-cli/src/update/tests.rs` and `crates/tiles-cli/tests/update.rs`; never run against the real releases repository on the development Mac without `TILES_BIN_DIR` pointing into `target/verify/`.
- `version-stamp`: a build with `TILES_VERSION=<tag without v>` prints it in `tiles --version`; the release job builds that way and stops when the two differ.
- `licence`: `tiles --licence` prints three lines: the code's licence (FSL-1.1-ALv2, `LICENSE`), the design assets, and the SIL Open Font License for Inter. A build that took a pack names `Design pack <n>` under the Tiles Design Licence (`LICENSE-design`); a build from source names the plain theme under the code's licence (ADR-040). No line says placeholder.
- `design-pack`: a build with `TILES_DESIGN_PACK=<file>` embeds that pack's sealed tokens when `scripts/design-pack.sha256` pins its hash, and stops with one line naming both hashes when it does not (ADR-036); the official release carries the sealed design pack, and a build from source draws the plain theme.
- `omni-set-key`: `tiles omni set-key <url>` reads the key with echo off and creates the Keychain items `tiles.omni/url` and `tiles.omni/api-key@<host>`, so only `tiles` reads them without a prompt (ADR-013), then sets the Tiles tools to ask in the OpenCode and Codex installs Tiles made. Covered by `crates/tiles-cli/src/omni.rs` and `install.rs` against a fake store and fake homes; never run on the development Mac, where it would write the login Keychain.
- `install-script` checks `SHA256SUMS.sig` against the release key it pins with `ssh-keygen -Y verify` before it trusts `SHA256SUMS`, and installs nothing, printing one line, when the signature is missing (downloaded, or beside `TILES_SUMS`), made by another key or namespace, or no longer matches (ADR-056); it checks the archive against `SHA256SUMS` and refuses a mismatch, and downloads with curl over HTTPS only from the releases repository (ADR-022) or the repository `TILES_RELEASES_REPO` names (ADR-032); it never calls `gh` (ADR-038). It removes `com.apple.quarantine` from its copy of the archive, the unpacked binary and the installed one (`xattr -s`), and when the installed `tiles --version` fails or prints nothing it exits 1 naming Gatekeeper, endpoint security and System Settings > Privacy & Security, never `installed ()` (ADR-035). Piped into `sh`, as `curl -fsSL <release>/install.sh | sh` runs it, it runs `tiles setup` reading the terminal at `/dev/tty` when stdout is a terminal, and with no terminal it prints the next step (ADR-059).
- `package`: `sh scripts/package-macos.sh <dist> <tag>` checks both tarballs' hashes, writes `tiles-<tag>-macos.pkg` and its `.sha256`, holding a universal ad-hoc-signed `/usr/local/bin/tiles`, `/usr/local/share/tiles/{LICENSE,LICENSE-design,tiles-setup.command}` and a postinstall that runs `launchctl asuser <uid> sudo -u <user> open -a Terminal /usr/local/share/tiles/tiles-setup.command`, or prints `open Terminal and run tiles setup` and exits 0. Covered by `sh scripts/test_package.sh`; never install the package on the development Mac.
- `update-from-package`: `tiles update` run from `/usr/local/bin/tiles` with no `TILES_BIN_DIR` exits 1 saying to download `tiles-<tag>-macos.pkg` and open it; `--check` and the daily notice read `Tiles vX.Y.Z is available; download tiles-vX.Y.Z-macos.pkg from its release and open it`, never `run tiles update` (`a_tiles_the_package_installed_is_updated_by_the_next_package` and `the_check_runs_at_most_once_a_day_and_never_when_off` in `update/tests.rs`).
- `release-binary`: a build with `RUSTFLAGS="$(sh scripts/release-rustflags.sh)"` passes `scripts/check-release-binary.py`: no source path, and the forms and tokens sealed (ADR-022).

## How to get to it (user POV)

- `tiles setup --dry-run`, `tiles setup`, `tiles install --dry-run opencode`, `tiles doctor`, `tiles check --tag v0.1.1`, `tiles update --check`, `tiles update`, `sh scripts/install.sh`.

## Driving it with drive.sh

Preconditions:

- `scripts/doctor.sh` passes. Never run `tiles install`, or `tiles setup` without `--dry-run`, on the development Mac outside a temporary `HOME` with stub harnesses first on `PATH`: they write the user's harness config.

- **Dry runs.** `drive.sh <run> install-dry-<h> install --dry-run <h>` per harness: Pi and OpenCode list `write` steps under the home folder; Claude shows `run claude mcp add --scope user tiles -e TILES_DRAW=text -- <tiles> mcp`; Codex `run codex mcp add tiles --env TILES_DRAW=text -- <tiles> mcp` and `write <codex home>/skills/tiles-theme/SKILL.md` (the `$tiles-theme` skill), and with Omni configured (`--env TILES_OMNI_URL=https://acme.omniapp.co --env TILES_OMNI_API_KEY=planted`) a second step `set default_tools_approval_mode = "prompt" under [mcp_servers.tiles] in <codex home>/config.toml`; a `config.toml` under `CODEX_HOME` whose `[mcp_servers.tiles]` sets that key to `approve` makes the dry run exit 1 and leaves the file as it was.
- **Cache clear.** With `C=--env TILES_CACHE_DIR=$PWD/target/verify/<run>/cache` on each, never the real cache: `drive.sh <run> cache-card $C card crates/tiles-engine/tests/intents/column.json`, then `drive.sh <run> cache-clear $C cache clear` reads `Removed 1 card.`, and `drive.sh <run> cache-doctor $C doctor` shows `(0 saved)`.
- **Doctor.** `drive.sh <run> doctor doctor`: lines `terminal:`, `answers:`, `cell size:` (then, on the text route, `pictures:` saying cards will not draw inline in this terminal, which terminals draw them, and that `tiles run` shows them in one window beside it, ADR-046), `overrides:`, `harnesses:` with one line per harness, each with its version and `(proved on <version>)`, and, under `opencode`, a second starting `OpenCode <version>, sst/opencode's CLI:`, `cards:`, `omni:`, `update check:` and `network:`.
- **Update.** `drive.sh <run> update-steps --env PATH=/usr/bin:/bin --env TILES_BIN_DIR='$OUT/bin' update`: exit 1, `tiles: gh is not on PATH, so tiles update cannot download the release itself. Download it by hand:` and three numbered steps, the first naming `https://github.com/tileshq/tiles/releases/latest`; nothing written to `$OUT/bin`. `drive.sh <run> update-check --env TILES_BIN_DIR='$OUT/bin' update --check` with the real `gh` signed in reads `Tiles v<latest> is available; run tiles update` (a development build is 0.0.0). The download and replace are driven against a fake `gh` by `cargo test -p tiles-cli --test update`.
- **Check.** `drive.sh <run> check-warp --env TILES_TERMINAL=warp --env TILES_ROUTE=kitty-precut check --tag v0.0.0`: every line starts `pass ` or `fail `; the terminal line reads `warp inside tmux, route kitty-precut`, the rows line `TILES_ROWS=40 on the kitty-precut route, so a card stands at most 30 rows` (the pane is 40 rows), each harness on `PATH` is `drawn by the wrapper`, and `fail graphics:` with exit 1, since tmux answers no kitty graphics query. The Warp-only cell line (the window size read as points) is covered by `cargo test -p tiles-cli check::`; Warp itself is checked by hand on a laptop ([laptop-check.md](../../../../docs/laptop-check.md#warp)).
- **Version stamp.** `TILES_VERSION=9.9.9 cargo build --locked -p tiles-cli`, then `target/debug/tiles --version` prints `tiles 9.9.9 (intent schema 1)`.
- **Licence.** `drive.sh <run> licence --licence`: exit 0 and three lines, `Code: FSL-1.1-ALv2, ...`, `Design assets (built from source): the plain theme, under the code's licence` and `Inter font: the SIL Open Font License 1.1`.
- **Design pack.** The official release carries the sealed design pack, and a build from source draws the plain theme: `tiles theme` lists dark and light where the release lists obsidian, light and dark (ADR-037). Write any bytes to a file named `tiles-design-1.pack` under `$OUT` and build with `TILES_DESIGN_PACK="$OUT/tiles-design-1.pack" cargo build --locked -p tiles-cli`: the build stops with `error: TILES_DESIGN_PACK=...: tiles-design-1.pack has SHA-256 <hash>, but scripts/design-pack.sha256 pins <hash>; this is not the pinned pack`. Build once more without the variable before driving anything else.
- **Doctor with half an Omni setup.** `drive.sh <run> doctor-mixed --env TILES_OMNI_URL=https://collector.evil.test doctor`: `omni: not configured: TILES_OMNI_URL is set but not TILES_OMNI_API_KEY`, so an environment URL never takes the Keychain key.
- **Release binary.** `RUSTFLAGS="$(sh scripts/release-rustflags.sh)" cargo build --release --locked -p tiles-cli`, then `python3 scripts/check-release-binary.py target/release/tiles --forbid "$PWD" --forbid "$HOME"` prints `no source path and no readable form, token or colour`, and `tiles forms` and `tiles render` still work, which shows the sealed assets open.
- **Setup.** `drive.sh <run> setup-dry --env HOME='$OUT/home' --env PATH='$OUT/path:/usr/bin:/bin' --env TILES_OMNI_URL=https://acme.omniapp.co setup --dry-run` after writing stub `pi`, `opencode`, `claude` and `codex` scripts into `$OUT/path` (as `machine` in `crates/tiles-cli/tests/setup.rs` writes them): each harness `not set up`, the `Tiles will change:` steps, `Dry run: nothing changed.`, and nothing under `$OUT/home`. The answers themselves are driven against the same stubs by `cargo test -p tiles-cli --test setup`.
- **Old copy.** Write `$OUT/old/tiles` as `#!/bin/sh` and `echo 'tiles 0.1.2 (intent schema 1)'`, symlink `$OUT/new/tiles` to `target/debug/tiles`, and run `$OUT/new/tiles setup --dry-run` and `$OUT/new/tiles doctor` with `PATH=$OUT/old:$OUT/new:$OUT/path:/usr/bin:/bin` and `HOME=$OUT/home`: setup names the old copy `comes first on PATH` and, listing no move, prints `To move $OUT/old/tiles aside, run: mv -n ...` (the debug build is 0.0.0, a development version, so the copy counts as one it cannot compare), doctor's second line ends `move it aside: mv -n $OUT/old/tiles $OUT/old/tiles-0.1.2-old`, and `$OUT/old/tiles` is still there. The question itself needs a terminal: `script -q /dev/null $OUT/new/tiles setup` with the same environment, answering `y`, renames it to `tiles-0.1.2-old`.
- **Installer.** `sh scripts/test_install.sh`: a good archive installs, a tampered one is refused, a `SHA256SUMS` rewritten under an old signature, signed by another key or namespace, damaged or unsigned is refused in one line (a local install and a release download alike), the pinned key is the release key by its fingerprint, `docs/install.md` prints the pinned key and the script's SHA-256, a quarantined download installs with the flag removed, a binary that prints no version or dies is refused with the Gatekeeper message, under a pseudo-terminal it runs `tiles setup`, piped into `sh` under one it runs `tiles setup` reading `/dev/tty`, and otherwise prints `next: tiles setup`, and without an archive curl downloads the release from the releases repository (or `TILES_RELEASES_REPO` or `TILES_REPO`), never the source repository, never calls `gh`, and a tag that could name another path or a failed download installs nothing.
- **Package.** `sh scripts/test_package.sh` on macOS: one universal package from two stub binaries, a tampered tarball refused, and the postinstall's Terminal launch and next-step lines.

## Gotchas

- Doctor or check run with stdin and stdout both pipes (an agent's tool call) says `answers: not asked (stdin and stdout are not terminals)` and `fail graphics: not asked; stdin and stdout are not terminals`, writing nothing to any terminal; with one a pipe and `/dev/tty` unopenable it names `/dev/tty` and why; piped inside a terminal, both ask `/dev/tty` and report as an unpiped run does.
